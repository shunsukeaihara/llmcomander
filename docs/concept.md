# LLM Commander コンセプト(ドラフト)

声で指揮するリアルタイムストラテジー。
RTSの面倒な部分、つまり細かい並列操作をLLMに任せ、プレイヤーは言葉で意図と方針を伝えることに集中する。

> このドキュメントは対話で決めた内容をまとめたもの。「未決定」の項目はまだ議論中。

## 1. ゲームの骨格

| 項目 | 決定内容 |
|---|---|
| ジャンル | StarCraft / Age of Empires 系の2D RTS |
| 内政 | AoE的。採掘・生産・建設・村人の割り当て |
| 兵種 | 槍・騎兵・弓の三すくみ |
| 時間 | 普通のリアルタイム(一時停止やスローはなし) |
| 対戦相手 | ある程度決定論的なルールベースAI |
| 表現 | AoEらしいドット絵のクオータービュー(アイソメトリック)。3Dはやらない |

## 2. プレイヤーの立ち位置と指示の粒度

プレイヤーは「戦術まで口を出す指揮官」。方針だけ出す将軍ではない。

- **内政はきっちり指示する**
  - 例:「木に8人、金に3人」「村人は常時生産」「木のうち5人を残して、残りは金へ」
- **戦闘は役割と振る舞いを指示する**
  - 例:「槍を盾にして騎兵を展開」「弓は敵と距離を保ち、軍事ユニットを優先して射撃」
- **場所は緩い指示でもよい**
  - 例:「村の中心は金鉱の近くに」

## 3. 入力

- **音声で指示する。** プッシュトゥトーク(キーを押している間だけ聞く)を想定。
- **従来型のRTS操作(右クリック移動など)はなくす。** ユニットを動かすのは必ず声。
- **GUIは選択と目印付けだけ。**
  - ユニットを選ぶ。
  - 地図に点・線・範囲を置き、名前を付ける(例: 防衛線A、集合地点B)。
  - 集合地点も「目印を置く」だけで、意味は声で与える(「新兵はここに集合」)。
- 発話中のクリックや選択と指示語を結び付ける(「**ここ**に塔」「**こいつら**は待機」)。

## 4. 実行と確認

| 種類 | 扱い |
|---|---|
| 内政・建設 | 確認してから実行する。建設予定地を地図上に半透明で仮置きし、「OK」かキーで確定、言い直しで修正 |
| 戦闘 | 即時に実行する。解釈の結果だけを表示する |

## 5. 指示のモデル: 作戦

指示は一つずつバラバラに扱わず、**作戦**単位にまとめる。

- 発話のたびに、LLMが既存の作戦を更新するか、新しい作戦を作るかを判断する。
  - 例:「弓は引き撃ち、他は撤退」は、戦線Aという作戦の中身の更新として扱う。
- 内政も同じ扱いにする(経済、第2拠点の開拓など)。
- **ユニットは一度に一つの作戦にだけ属する。** 移すとカード間を移動する。
- 作戦の作成・統合・解散は声で行い、LLMが処理する。GUIで直接いじる操作は必要になったら足す。
- 指示の寿命は3種類。
  - 一回きりの行動(〜へ移動)
  - 解除するまで続く規則(常に引き撃ち)
  - 条件が満たされたら発動(敵が防衛線Aに接触したら騎兵を展開)

## 6. LLMとゲームの役割分担

| 層 | 頻度 | 担当 |
|---|---|---|
| 移動・経路探索・自動攻撃・採掘の往復 | 毎フレーム | ゲーム(確定的) |
| 個体の選択、建設候補地の算出 | 指示のたび | ゲーム(確定的) |
| 作戦ごとの戦術判断・状況要約 | 数秒ごと | 作戦ごとのLLM担当者(並列) |
| 発話の解釈、作戦への振り分け | 発話のたび | 司令LLM |

原則は次の4つ。

- **作戦1つをLLMの担当者1人が受け持つ。** 「並列で動くLLM」の単位がそのまま作戦になる。
- **LLMは意図と数を決め、ゲームは具体的な個体と座標を決める。**
  - 例: LLMは「木から金へ3人」とだけ決める。どの村人を動かすかは、ゲームが距離や運搬中かどうかで選ぶ。
  - 例: 場所は、ゲームが候補地を特徴付きで出し、LLMが選ぶ。LLMに生の座標は考えさせない。
- **ユニットはLLMを待たない。** 今設定されている規則で常に自律的に動き、LLMの結果は届いた時点で差し替えるだけ。
- **戦闘の振る舞いは部品とパラメータの組み合わせで表す。** 目標優先度、保つ間合い、隊列での位置、護衛対象、交戦・撤退の条件など。
  - 「受け止めたら展開」の判定のように、判断が要るところはLLMの担当者が見直す。

## 7. 情報提示(UI)

フィードバックは声で返さず、画面で見せる。UIの主役は「LLMが何をしようとしているか」を見せること。

- **地図上に意図を重ねる**
  - 部隊ごとの指示バッジ、移動予定の矢印、条件付きの動き(点線と条件ラベル)
  - 引き撃ちの範囲、建設の仮置き、警報
- **稼働中の作戦の一覧**
  - 作戦ごとのカードに、役割ごとの行動、状況(隊列、優先攻撃先、損害)、直前の変更を表示する。
- **上書きの可視化**
  - 置き換えられた指示は取り消し線で残し、どの発話で変わったかを示す。
- **内政パネル**
  - 割り当ての目標と実際の差を表示する(例: 金 5/6、1人移動中)。
- **指示履歴**
  - 発話 → どの作戦をどう変えたか、を時系列で並べる。

## 8. グラフィック

- **地図**はドット絵のクオータービュー。
- **UI**はドット絵にせず、読みやすい現代的なデザインを地図の上に重ねる。作戦カードなど情報量の多い部分の読みやすさを優先する。
- **素材**は生成で作る。
  - 一番難しいのは、向きやアニメーションの各コマで見た目を揃えること。
  - 建物は1方向だけでよく、地形のタイルも生成しやすい。ユニットのアニメーションが最大の課題になる。
  - 陣営の色はパレットの差し替えで出し、生成する枚数を減らす。
  - ゲーム本体の開発は素材を待たない。仮素材で進め、素材の生成手順は並行して検証する。

## 9. 技術スタック

- ドット絵のクオータービューで、UI/UXまで含めて自作する。既存RTSには乗らない。
- エンジン候補(**未決定**)。
  - **Godot 4**: 第一候補。2DとUIが強く、アイソメトリックのタイルマップも標準で扱える。
  - **Bevy**: 大量ユニットに強いが、UIは手薄。
- LLM層はゲームとは別プロセスにする想定。通信方式やゲームロジックの置き場所は**未決定**。
