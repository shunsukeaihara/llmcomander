# LLM Commander コンセプト(ドラフト)

声で指揮するリアルタイムストラテジー。
RTSの面倒な部分、つまり細かい並列操作をLLMに任せ、プレイヤーは言葉で意図と方針を伝えることに集中する。

> このドキュメントは対話で決めた内容をまとめたもの。「未決定」の項目はまだ議論中。

## 1. ゲームの骨格

| 項目 | 決定内容 |
|---|---|
| ジャンル | StarCraft / Age of Empires 系の2D RTS |
| 内政 | AoE的。採掘・生産・建設・村人の割り当て |
| 兵種 | 槍・騎兵・弓の三すくみ |
| 技術 | 軽め。2〜3段階の時代進化と、少数のアップグレード(攻撃+1、鎧+1、採掘効率など) |
| 陣営 | プレイヤーと敵AIは同じ陣営(兵種と性能が同じ)。文明ごとの違いは後回し |
| 時間 | 普通のリアルタイム(一時停止やスローはなし) |
| 対戦相手 | ある程度決定論的なルールベースAI |
| 規模 | 1試合25〜35分、人口上限100前後。内政の拡張と複数の戦線を同時に回す規模 |
| 対戦形式 | 1対1(プレイヤー vs 敵AI)。複数の敵や味方AIとのチーム戦は後回し |
| マップ | 手で作った固定マップを数枚。広さはAoE2の1対1マップよりやや小さい程度。地名を付けてLLMと共有する。ランダム生成は後回し |
| 表現 | AoEらしいドット絵のクオータービュー(アイソメトリック)。3Dはやらない |

## 2. プレイヤーの立ち位置と指示の粒度

プレイヤーは「戦術まで口を出す指揮官」。方針だけ出す将軍ではない。

- **内政はきっちり指示する**
  - 例:「木に8人、金に3人」「村人は常時生産」「木のうち5人を残して、残りは金へ」
- **戦闘は役割と振る舞いを指示する**
  - 例:「槍を盾にして騎兵を展開」「弓は敵と距離を保ち、軍事ユニットを優先して射撃」
- **場所は緩い指示でもよい**
  - 例:「村の中心は金鉱の近くに」

## 3. 入力

- **音声で指示する。** プッシュトゥトーク(キーを押している間だけ聞く)を想定。
- **従来型のRTS操作(右クリック移動など)はなくす。** ユニットを動かすのは必ず声。
- **GUIは選択と目印付けだけ。**
  - ユニットを選ぶ。
  - 地図に点・線・範囲を置き、名前を付ける(例: 防衛線A、集合地点B)。
  - 集合地点も「目印を置く」だけで、意味は声で与える(「新兵はここに集合」)。
- 発話中のクリックや選択と指示語を結び付ける(「**ここ**に塔」「**こいつら**は待機」)。

## 4. 実行と確認

| 種類 | 扱い |
|---|---|
| 内政・建設 | 確認してから実行する。建設予定地を地図上に半透明で仮置きし、「OK」かキーで確定、言い直しで修正 |
| 戦闘 | 即時に実行する。解釈の結果だけを表示する |

## 5. 指示のモデル: 作戦

指示は一つずつバラバラに扱わず、**作戦**単位にまとめる。

- 発話のたびに、LLMが既存の作戦を更新するか、新しい作戦を作るかを判断する。
  - 例:「弓は引き撃ち、他は撤退」は、戦線Aという作戦の中身の更新として扱う。
- 内政も同じ扱いにする(経済、第2拠点の開拓など)。
- **ユニットは一度に一つの作戦にだけ属する。** 移すとカード間を移動する。
- 作戦の作成・統合・解散は声で行い、LLMが処理する。GUIで直接いじる操作は必要になったら足す。
- 指示が前の指示と矛盾したときは、LLMの解釈に任せ、確認待ちはしない。結果はカードと履歴に表示し、おかしければプレイヤーが追加の指示で直す。
- 指示の寿命は3種類。
  - 一回きりの行動(〜へ移動)
  - 解除するまで続く規則(常に引き撃ち)
  - 条件が満たされたら発動(敵が防衛線Aに接触したら騎兵を展開)

## 6. LLMとゲームの役割分担

| 層 | 頻度 | 担当 |
|---|---|---|
| 移動・経路探索・自動攻撃・採掘の往復 | 毎フレーム | ゲーム(確定的) |
| 個体の選択、建設候補地の算出 | 指示のたび | ゲーム(確定的) |
| 作戦ごとの戦術判断・状況要約 | 数秒ごと | 作戦ごとのLLM担当者(並列) |
| 発話の解釈、作戦への振り分け | 発話のたび | 司令LLM |

原則は次の4つ。

- **作戦1つをLLMの担当者1人が受け持つ。** 「並列で動くLLM」の単位がそのまま作戦になる。
- **LLMは意図と数を決め、ゲームは具体的な個体と座標を決める。**
  - 例: LLMは「木から金へ3人」とだけ決める。どの村人を動かすかは、ゲームが距離や運搬中かどうかで選ぶ。
  - 例: 場所は、ゲームが候補地を特徴付きで出し、LLMが選ぶ。LLMに生の座標は考えさせない。
- **ユニットはLLMを待たない。** 今設定されている規則で常に自律的に動き、LLMの結果は届いた時点で差し替えるだけ。
- **戦闘の振る舞いは部品とパラメータの組み合わせで表す。** 目標優先度、保つ間合い、隊列での位置、護衛対象、交戦・撤退の条件など。
  - 「受け止めたら展開」の判定のように、判断が要るところはLLMの担当者が見直す。

## 7. 情報提示(UI)

フィードバックは声で返さず、画面で見せる。UIの主役は「LLMが何をしようとしているか」を見せること。

- **地図上に意図を重ねる**
  - 部隊ごとの指示バッジ、移動予定の矢印、条件付きの動き(点線と条件ラベル)
  - 引き撃ちの範囲、建設の仮置き、警報
- **稼働中の作戦の一覧**
  - 作戦ごとのカードに、役割ごとの行動、状況(隊列、優先攻撃先、損害)、直前の変更を表示する。
- **上書きの可視化**
  - 置き換えられた指示は取り消し線で残し、どの発話で変わったかを示す。
- **内政パネル**
  - 割り当ての目標と実際の差を表示する(例: 金 5/6、1人移動中)。
- **指示履歴**
  - 発話 → どの作戦をどう変えたか、を時系列で並べる。

UIモック: https://claude.ai/artifact/CpjfajogNU6hjMcg4Me46S (非公開。閲覧には共有設定が必要)

## 8. グラフィック

- **地図**はドット絵のクオータービュー。
- **UI**はドット絵にせず、読みやすい現代的なデザインを地図の上に重ねる。作戦カードなど情報量の多い部分の読みやすさを優先する。
- **素材**はBlenderで作る(無料、GPU不要)。
  - ローポリの3Dモデルをコードで組み、アイソメトリックの固定角度から描画して、ドット絵に変換する(`tools/sprites/`)。
  - 3Dを経由するので、向きやコマが変わっても見た目が揃う。8方向でも作業量はほとんど増えない。
  - 陣営の色は、決めた色の部分を差し替えて出す。
  - 画像生成AIや3D生成AIを使う方法も調べた。無料枠の制約やライセンスの不確かさがあり、今は使わない。
  - ゲーム本体の開発は素材を待たない。

## 9. 技術スタック

- ドット絵のクオータービューで、UI/UXまで含めて自作する。既存RTSには乗らない。
- **Godot 4(C#)で全部作る**。描画、UI、シミュレーション、マイク入力、LLMと音声認識の呼び出しまで、一つのプロセスで行う。
  - LLMは公式の C# SDK(Anthropic / OpenAI)から呼ぶ。作戦ごとの担当LLMは async で並列に呼ぶ。
  - APIキーはゲーム本体が持つ。他人に配る段階で、各自がキーを入れるか中継サーバーを立てるかを決める。
- LLMと音声認識は、クラウドのAPI(Claude または OpenAI)を使う。PoCの段階では、API費用より応答の質と速さを優先する。

## 10. PoCの範囲と現状

確かめたいことは「声で指示して、LLMが並列にユニットを動かすのが気持ちいいか」。

**作ったもの**
- 固定マップ1枚、村人の採掘と生産、村の中心と兵舎、槍・弓・騎兵の三すくみ
- 交戦規則の部品(待機・進撃・撤退、場所、横隊、引き撃ち、優先目標、条件付きの動き)
- 発話 → 司令LLM → 作戦カード、作戦ごとの担当LLM(状況の要約と細部の調整)
- 霧: ユニットと建物の周りだけが見える。LLMに渡すのは見えている敵と、最後に見た位置の記録、見たことのある敵の建物だけ。ユニットも見えている敵しか狙わない(敵AIは霧の影響を受けない)
- 建設候補地: 発話ごとにゲームが建物の種類別に候補地を計算し、特徴(資源までの距離、基地からの距離、敵の目撃)付きでLLMに渡す。LLMは条件に合う候補を名前で選ぶ。合う候補がなければ地名や目印で指定する
- 司令LLMの応答はストリーミングで受け取り、命令が1つ完成するたびに、応答の残りを待たずにゲームへ反映する
- 作戦カード、地図上の意図表示、上書きの取り消し線、指示履歴(応答時間付き)、建設の確認
- 時間割で動く敵AI(内政と、一定間隔の攻撃の波)

**PoCで簡略化したところ**
- 時代進化、技術、複数マップは未実装

**まだ確かめていないこと**
- 実際のLLMでの応答時間と解釈の正しさ(`tools/bench` で計測できる)
- 音声認識の精度と遅延、担当LLMの判断の質
